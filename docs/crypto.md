# Cryptography on a Roku 2 XS

AirPlay pairing needs X25519 and Ed25519, and the stream keys need FairPlay (playfair) decryption. Roku OS gives BrightScript only a few native primitives:

| Native (fast) | Not available |
|---|---|
| `roEVPDigest`: SHA-1/256/512, MD5 | Any elliptic-curve or big-integer API |
| `roEVPCipher`: AES-CBC/CTR/ECB, keeps CTR state across `Update` calls | XOR, arithmetic right shift, unsigned types |
| `roDeviceInfo.GetRandomUUID()` | A CSPRNG API |

So the curve arithmetic is written in BrightScript. Speed is the main constraint:

- **Integer vs LongInteger.** On this CPU, a 32-bit `Integer` multiply-add costs about 1 µs. `LongInteger` and `Double` are 20–30× slower.
- **Field multiplication.** Even a carefully unrolled field multiplication takes about 0.7 ms.

## Field arithmetic: GF(2^255−19) in 32-bit Integers (`fe25519.brs`)

`fe25519.brs` is **generated** by `tools/gen_fe25519.py`; never edit it by hand. The generator also self-checks the bounds described here.

- **Representation.** 20 limbs of 13 bits, 260 bits in all, each held in a plain `Integer`.
- **Why 13 bits.** A product of two 20-limb numbers has 39 column sums. Each must stay under 2^31 so it never overflows or wraps a signed 32-bit Integer. With limbs below `LIMB_MAX = 10362`, `20 · 10362² < 2^31`.
- **Reduction.** The column sums are carried into 13-bit digits. The top 20 digits are folded down using `2^260 ≡ 32 · 19 = 608 (mod p)`.
- **No negative intermediates.** Device `>>` is a logical shift, so a negative value would carry garbage. Subtraction `a − b` is computed as `a + SUBP − b`, where `SUBP` is a multiple of p whose limbs are all ≥ `LIMB_MAX`, so every limb stays non-negative.
- **No reliance on wrap.** On the device, Integer overflow wraps. In the local `brs` interpreter it doesn't. Code that stays below 2^31 gives the same result in both, so the local differential tests are trustworthy.
- **Lazy reduction.** Values stay non-canonical (below 2^260). `fe_tobytes` canonicalises them. Inversion uses the ref10 addition chain for `a^(p−2)`.
- **Aliasing.** Every routine is fully unrolled, with no loops or array-index arithmetic in the hot path, and the output may alias an input.

## X25519 (`curve25519.brs`)

- **Shared secret.** An RFC 7748 Montgomery ladder over 255 bits: about **1.85–1.9 s** on the device. This is the one expensive operation that has to happen while a sender waits, in pair-verify.
- **Public key from a private key.** This uses the Ed25519 fixed-base table and the birational map `u = (Z+Y)/(Z−Y)`. It is about 2× faster than the ladder.

## Ed25519

- **Fixed-base multiplication.** `assets/ed25519_base.bin` is generated by `tools/gen_ed25519_table.py`. It holds `2^i · B` for i = 0…254 in "niels" form: `(y+x, y−x, 2dxy)`, 96 bytes per entry. Then `s · B` needs one mixed addition per set bit and no doublings.
- **Identity.** A persistent 32-byte seed in the registry. The public key is computed once at startup (about 1.6 s) and advertised as `pk`.
- **Signing nonce.** Signing uses a **random nonce** instead of RFC 8032's deterministic `r = H(prefix ‖ msg)`.
  - `R = r · B` can then be computed **before** the message is known, in an idle "pool" step after startup and after each pairing.
  - The signature itself, `S = (r + H(R ‖ A ‖ M) · a) mod L`, then costs only hashing and scalar arithmetic.
  - A verifier can't tell the difference. The one rule, enforced by the pool, is that a nonce is never used twice.
- **Scalars mod L.** The TweetNaCl `modL` approach: 64 LongInteger limbs of radix 2^8. Floor division is done by hand, because `>>` is logical and LongInteger `/` is a float.
- **Randomness.** Six `GetRandomUUID()` values (v4, from the OS), the clock and `Rnd` are hashed with SHA-512 and extended by re-hashing.

### pair-verify timeline

| Step | When | Cost |
|---|---|---|
| Ephemeral X25519 key pair | idle precompute | ~1 s |
| Ed25519 nonce `R = r·B` | idle precompute | ~0.9 s |
| `X25519(priv, client_pub)` | during the request | ~1.85 s |
| Sign `our_pub ‖ client_pub` | during the request | ~0.27 s |
| AES-CTR on the signature, SHA-512 key derivation | during the request | negligible (native) |

The sender waits about **2.1 s**, well within iOS's timeout. Without the precompute it would wait about 4 s.

None of this is constant-time. The keys are ephemeral pairing keys on a single-user appliance, so timing side channels are out of scope, a choice noted in the source.

## FairPlay (`fairplay.brs`)

FairPlay "SAP" key exchange is what lets an AirPlay sender encrypt the session AES key. Senders only talk to receivers that complete it. `fairplay.brs` is a port of RPiPlay's `playfair`, the reverse-engineered implementation that every open-source receiver uses.

- **Tables.** The ~185 KB of lookup tables are extracted from the C sources by `tools/gen_fairplay_tables.py` into `assets/fairplay/*.bin`. They are loaded once at startup and cached in `GetGlobalAA().fp_tables`.
- **Phases.**
  - Phase 1: a canned 142-byte reply chosen by the request's mode byte.
  - Phase 2: a 12-byte header plus 20 bytes echoed from the request. The 164-byte request is kept for later.
  - `FairPlay_Decrypt(req164, ekey72)` returns the 16-byte AES key, in about **210 ms**.
- **uint32 arithmetic in signed Integers.** Values are kept as two's-complement bit patterns. Additions are done in 16-bit halves (`fp_add32`) so they never overflow. XOR is `(a or b) − (a and b)`. Right shifts of possibly-negative values are always masked.
- **Verification.** `test/fairplay/run.sh` compiles the original C into a harness and checks the BrightScript port byte-for-byte on random inputs.

## Key schedule summary

```
pairing:    shared   = X25519(eph_priv, client_eph_pub)
fp-setup:   keymsg   = 164-byte phase-2 request
SETUP:      aeskey   = FairPlay_Decrypt(keymsg, ekey)
            aeskey   = SHA-512(aeskey ‖ shared)[0:16]        (only if pairing happened)
mirroring:  key      = SHA-512("AirPlayStreamKey" + streamConnectionID ‖ aeskey)[0:16]
            iv       = SHA-512("AirPlayStreamIV"  + streamConnectionID ‖ aeskey)[0:16]
            AES-128-CTR, one continuous keystream across video packets
audio:      AES-128-CBC(aeskey, eiv), reset per RTP packet, whole blocks only
```

`streamConnectionID` is an unsigned 64-bit integer, often above 2^63. The plist reader keeps it as a LongInteger bit pattern, and `u64_str` prints it as an unsigned decimal using `\` and `mod` on LongIntegers, because `/` would go through a float and lose digits.
